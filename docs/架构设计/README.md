## 执行顺序

1. **先做 D-01–D-06 设计检查**：它们是文档层面的确认，不写代码。有任一项无法从现有文档得出唯一答案，停下来补文档，不要靠猜。
2. **搭贯穿真实链路的测试壳**：V-01（网络与后台生命周期）、V-03（恢复、并发、幂等）、V-05（IPC 授权）一起做，它们会同时暴露路由、生命周期与身份问题。
3. **再打失败路径**：用本地模拟中转站先覆盖冷启动、延迟响应头、断流、重试、转接、页面变化、拒绝读取。
4. **最后做真实环境**：公司 WiFi / UniVPN 的中转站与问题建议命中率必须由用户本人在真实环境执行；不要要求对方在对话里贴 Key。
5. **每项结果按第 5 节模板记录**，状态只能是：未执行 / 通过 / 失败 / 环境阻塞 / 接受降级。接受降级必须写明用户能看到的产品行为变化。

## 硬规则

1. **不要重开技术栈讨论。** 选型已定稿并经一轮评审，替换建议需要新决策（`../需求分析梳理/DECISIONS.md`）支撑。
2. **不要把 AR 编号当成未关闭的问题。** 26 项全部有处置，结论在 `REVIEW_RESPONSE.md`；「仍未关闭、需要实测」的清单在该文件第 6 节。
3. **改架构要升版本号**，更新文末变更记录，并同步受影响的需求条目；不要静默改正文。
4. **实测得到的新数值才回写架构**（`ARCHITECTURE.md` 5.15 与需求文档第 9 节，数字是参考值，决策 081）；用例结果记在 `../原型验证/记录/`，不要写进架构文档。
5. **未测就标「未测」**。不允许用「Chromium 通过」代替「Chrome / Edge 真实版本通过」，也不允许用「端口可达」代替「收到有效模型响应」。
