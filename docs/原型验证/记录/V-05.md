## 3. storage.local 收紧窗口的专项说明

`src/background/app.ts` 在每次后台启动时都调用一次 `deps.lockStorage()`（`browser.storage.local.setAccessLevel({accessLevel:'TRUSTED_CONTEXTS'})`），**不 await**，理由是不阻塞 `onMessage`/`onConnect` 监听器的同步注册（代码注释里已经写明“失败不当作安全保证”）。这意味着从后台这次启动的最早一刻到这次 `setAccessLevel` 真正生效之间，理论上存在一个内容脚本可以读到 `storage.local`（含 Key）的窗口。

**已验证**：

- 稳态下（后台已运行一段时间）内容脚本尝试 `chrome.storage.local.get()` 立即收到 `Access to storage is not allowed from this context.`，读不到任何数据——用 `chrome.scripting.executeScript({world:'ISOLATED'})` 注入探针直接验证，不是只看 UI 上的“已关闭”。

**未能可靠验证的部分**：

- 尝试过用 CDP `ServiceWorker.stopAllWorkers` 强制终止后台进程、再触发消息把它唤醒，同时从内容脚本以尽可能高的频率轮询 `storage.local`，试图在“刚唤醒、`lockStorage()` 尚未落定”的窗口里捕获一次成功读取。
- 多次尝试后判断：这条路径在工具层面不可靠——外部工具（Node 进程 → CDP → 浏览器）触发“唤醒”这个动作本身的开销（典型几十毫秒级）远大于 `setAccessLevel` 这个单次扩展 API 调用可能需要的时间（大概率是亚毫秒到个位数毫秒级的一次 IPC），即便唤醒信号先到，由它触发的新一次 `scripting.executeScript` 调用也只能在后台模块顶层代码（含 `lockStorage()` 调用）执行完之后才能被后台处理，天然错过了最早的那一小段窗口。这不是“测过了，确认没问题”，而是“黑盒测试工具的时间粒度打不穿这个窗口”。

**结论**：这一项记为**未执行**（环境/工具局限，不是「通过」也不是「失败」）。架构代码本身的注释已经承认这一点（“失败不当作安全保证”），本次验证确认了稳态下的保护有效，但没有能力证明或证伪“每次唤醒都存在的极短窗口”是否真实存在、能否被实际利用。

**退路 / 建议**：

- 产品代价：如果这个窗口真实存在且可被利用，代价是极端情况下（页面上已经有恶意内容脚本常驻，且精确撞上后台刚被唤醒的那一刻）可能读到 Key。由于窗口理论上是毫秒级且需要内容脚本持续高频轮询才有机会撞上，实际可利用性很低，但不能用「测过了」来背书。
- 不需要改架构：现有「每次启动都收紧一次」已经是这类问题里能做到的最好实践（没有办法让 `setAccessLevel` 变成同步或在监听器注册前完成而不阻塞监听器注册本身）。如果要进一步收窄，只能寄希望于浏览器把 `storage.local` 的访问级别做成跨重启持久化（这是浏览器实现细节，不是扩展能控制的）。
- 建议：保持现状，不升级为阻塞项；如果以后有合适的工具（比如能在浏览器进程内、比 Node 外部调用更快地触发探测的手段）再补测。

## 4. Edge 与 Chrome 的 sender 字段差异（真机实测）

真实运行 `tests/e2e/*.spec.ts` 时后台日志打印的 `senderSummary`（`src/background/roles.ts`）字段对照：

| 字段 | Chrome for Testing 159.x | Microsoft Edge 157（真机） | 差异 |
| --- | --- | --- | --- |
| `url`（已去掉片段） | `chrome-extension://pkahgpgifechjgdpecaebajnocgcnnnd/float.html` | 同左 | 无 |
| `urlHasFragment` | `true` | `true` | 无 |

| `frameId` | 观测到 `4` | 观测到 `3` | **有差异**：具体数值不同，但这只是两边渲染小窗宿主时 iframe 在页面里排第几个框架的布局差异（哨兵、阅读器、工具栏宿主、小窗宿主各占一个框架，顺序与两个浏览器的内部框架编号策略有关），不影响鉴权逻辑——鉴权只比较「这次握手的 frameId」和「写绑定时记的 frameId」是否一致，不关心具体数值 |
