## 1. 发现并修复的竞态：两个连接几乎同时对同一对话发问

### 1.1 问题

`jobs.ask()` 原来的检查顺序是：

```
const jobId = deps.newId();
byRequest.set(msg.clientRequestId, jobId);
const refuse = ...
const known = conversations.get(msg.conversationId);
if (known?.activeJobId !== undefined) return refuse('invalid');  // 检查
...（await store.getSelection、await deps.loadSettings 等好几个 await）...
conv.activeJobId = jobId;  // 真正占位，离检查已经隔了好几个 await
```

检查（`known?.activeJobId !== undefined`）和真正占位（`conv.activeJobId = jobId`）之间隔着好几次 `await`（取选区、读设置）。如果两个连接的 `conv/ask` 消息几乎同时到达，两次调用都会在"检查"那一刻看到 `activeJobId === undefined`（因为谁都还没来得及占位），于是都通过检查、都往后走、都真正发起了网络请求——同一个对话里出现了两个并发的在途任务，违反架构"同一对话正在生成时不排队、不自动停止"背后隐含的"同一时刻只有一个在途任务"的前提。

### 1.2 修复

把"占位"挪到检查之后、第一个 `await` 之前，在同一个同步段里完成"检查 + 占位"：

```ts
if (known?.activeJobId !== undefined) return refuse('invalid');
if (known) known.activeJobId = jobId;   // 同步段内立刻占位，关闭竞态窗口
...（后面的 await 不再能被第二次 ask 抢到）
```

同时 `refuse()`（这条请求后续失败，比如选区对不上、设置读取失败）必须把占住的 `activeJobId` 还回去，否则一次失败的发问会把对话"锁死"：

```ts
const refuse = (reason) => {
  byRequest.delete(msg.clientRequestId);
  if (known?.activeJobId === jobId) known.activeJobId = undefined; // 占位的回滚
  reject(reason);
};
```

修复文件：`src/background/jobs.ts`。

### 1.3 回归测试证明修复确实生效

`tests/unit/background/ask-flow.test.ts` 新增用例"两个界面同一对话几乎同时发问"：先用一个端口问完一轮拿到 `conversationId`，再开第二个端口（`resumeFloat` 复用同一标签页的绑定，模拟协议层的第二个并发连接），两个端口**同步**各发一条到同一个 `conversationId`，断言总共只接一单（只发一次网络请求），另一条被拒绝（`invalid`）。

**验证方法本身有效**：临时注释掉修复的那一行（去掉同步占位），重跑这条用例，确认它会失败（实际发出了 3 次网络请求，不是 2 次），恢复修复后再跑通过。这证明了新测试真的在防护这个竞态，不是摆设。

## 2. 「两个 UI 同时发问同一对话」的实际验证范围

架构要求验证"两个界面同一对话同时发送"。本版本产品上只有小窗一种界面，没有侧边栏。为了尽量验证到协议层的并发语义，第 1 节的回归测试用了"同一标签页上开两个 `CONV_PORT` 连接（模拟小窗的两次握手）"来逼近"两个 UI"的效果——这确实复现并修复了一个真实的竞态条件，但它不是"小窗 + 侧边栏"这个产品组合，而是同一种界面的两个连接。

**真正的「小窗 + 侧边栏同时发问」未执行（待侧边栏）**——按任务要求如实记录，不冒充已验证。好消息是：竞态修复发生在 `jobs.ask()` 里，与调用方是小窗还是侧边栏无关（侧边栏接入后走的是同一个 `jobs.ask()` 入口），所以第 1 节的修复对未来的侧边栏场景同样适用，只是还没有侧边栏代码可以实际跑一遍端到端验证。

## 3. 检查点间隔中终止后台、重新打开（interrupted 全链路）

新增 e2e：`tests/e2e/retry.spec.ts`「流式中途后台被回收：重连后标记 interrupted，提示「结果未知」，仍可点「重试」」。

步骤：用 `long` 模式发问，等收到第一批正文后，用调试协议 `ServiceWorker.stopAllWorkers` 直接停掉后台（效果等价于真机空闲被回收，见 `prototypes/net-probe/RESULT.md` 的真机结论）。

实测结果：
- 小窗检测到长连接端口断开、且有未到终态的任务，立即用 `conv/resumeFloat` 重连（`src/ui/float/state.ts` 的 `onPortDisconnect`）。
- 新后台实例启动扫描（`createJobs` 里的 `ready`）发现这个任务的 `workerEpoch` 跟新实例不一致、且未到终态，标记为 `interrupted`，原因 `workerRestarted`。
- 客户端收到 `conv/jobState`（`state: interrupted`）：界面任务状态区变成 `interrupted`，显示「上次请求的结果未知，重试可能重新计费」（新加的文案，`src/ui/FloatApp.tsx`）。
- 已经收到的那部分正文**原样保留**，没有被清空（验证了 `job.ts` 文件头"保留已生成部分"的承诺）。
- 「重试」按钮出现（`canRetry('interrupted') === true`）。

### 3.1 点击「重试」之后：一个诚实记录的已知局限

点击「重试」后，请求被服务端拒绝，原因 `notOwner`。**原因**：重试要靠 `jobs.retry()` 从**内存**里的 `Job` 对象原样取出上次装配好的 `conn/adapter/req` 重发（`job.ts` 文件头："不是新发问，不重新装配"）。但跨后台重启后，旧进程的内存（包括这个 `Job` 对象）已经随进程消失，新进程的任务表里没有这个 `jobId`。`JobRecord`（存在 `storage.session` 里的热副本）只保存了状态元信息，没有保存原始请求装配结果（选区文字、提示词、模型参数等），所以**无法在新进程里凭空重建出"原样重发"所需的请求体**。

这与架构 V-03 的"失败退路"原文一致："缺少确认时不偷偷重发，提供可辨认的重试入口；恢复只保证保存内容和状态，不宣称恢复同一网络流"——重试入口确实给出来了（按钮可见），但"可辨认"目前止步于界面弹出一条"操作失败"提示，文案是通用的 `rejectReasonText('notOwner')`（"无权限操作该任务"），对用户来说容易误解成权限问题而不是"后台重启过，这条任务没法重试，请重新提问"。

**产品代价**：用户在后台被回收后看到「重试」按钮，点了却得到一条不好理解的报错，还得自己想到"换一种方式重新提问"。

**后续处理**：按决策 070，重试被拒时改用专属文案——后台已重启：「后台已重启，这次没法重试，请重新提问」；请求还没发出就被停掉：「这次请求没有发出，没法重试，请重新提问」（`src/ui/float/state.ts` 的 `retryRejectedText`，`b79ea25`）。跨重启保存原始请求以支持重试不做（要把装配好的内容连同页面正文落盘，隐私代价大于收益）。

**建议的后续修复（本次未做，保持改动范围）**：
1. 最小代价：把 `notOwner` 在 `conv/retry` 场景下的提示文案改得更明确（例如"该任务所在的后台已重启，无法重试，请重新提问"），这只需要在界面层区分一下 `refType`，不改协议。
2. 更彻底但代价更大：把请求装配结果（至少是 messages 数组）也写进 `JobRecord` 持久化，这样跨重启也能重试——但这会显著增大 `storage.session` 的写入量（每次请求都要把完整提示词随检查点写一遍），需要重新评估 5.15 的性能预算，不建议在不权衡的情况下直接做。

本次选择如实记录这个边界，而不是回避它或在不改变架构约束的情况下强行让它"看起来通过"。

## 4. 重试（`conv/retry`）功能实现

### 4.1 之前的状态

`src/background/conv.ts` 原来对 `conv/retry` 直接落到 `default` 分支，回 `notAllowed`（功能未实现）。

### 4.2 本次实现

- `src/core/domain/job.ts`：`JOB_LIMITS` 新增 `connectTimeoutMs`（见 V-01），`canRetry` 已有（判断 `failed`/`interrupted`/`stopped` 三种终态可重试），本次复用。
- `src/background/jobs.ts`：
  - `Job` 接口新增 `conn`/`adapter`/`req` 三个字段，在 `ask()` 建任务时原样存下，供重试直接复用（不重新装配，符合 `job.ts` 文件头注释的既定设计）。
  - 新增 `retry(tabId, jobId)`：校验任务属于这个标签页、状态可重试；重置 `controller`/`answer`/`reasoning`/`pendingText` 等运行时字段，生成新 `attemptId`、`attempt+1`，状态回到 `accepted`；把 `conv.activeJobId` 重新指回这个 `jobId`（否则重试期间这个对话又会被当成"空闲"，允许新的 `conv/ask` 插进来）；原样调用 `run(job, job.conn, job.adapter, job.req)`。
- `src/background/conv.ts`：`conv/retry` 接入 `jobs.retry()`。
- `src/ui/float/state.ts`：
  - `applyJobState` 放开了"终态不可覆盖"的限制——**只放开重试这一个例外**：同一 `jobId` 但 `attemptId` 变化时，允许从终态（如 `failed`）回到 `accepted`。这是故意的、唯一的跳出终态路径，注释里写明了理由。
  - `applyDelta` 的"新尝试判定"从只看 `attemptId !== view.attemptId` 改成 `attemptId !== view.attemptId || !view.attemptStarted`。**这是本次 e2e 测试中发现的一个真实客户端 bug**：重试的 `conv/jobState`（带新 `attemptId`）通常先于它的第一条 `conv/delta` 到达，到增量消息送达时 `view.attemptId` 已经被 `applyJobState` 同步成新值了，这时候单看"`attemptId` 是否变化"已经看不出"是不是这次尝试的第一条增量"，原逻辑会把重试后的新内容追加在旧内容后面（界面上出现"旧答案+新答案"拼接在一起）。改成同时看 `attemptStarted`（这次尝试是否已经收到过增量）后，e2e 测试里不再出现拼接。
- `src/ui/FloatApp.tsx`：在任务状态区新增「重试」按钮（`canRetry(job.state)` 时显示）与 `interrupted` 状态下的提示文案。只在这一块加了改动，没有碰另一位同事正在改的小窗其它 UI 区域。
