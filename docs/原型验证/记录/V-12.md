## 发现：拖动 / 缩放的实现从「iframe 内捕获」改为「宿主侧不可见把手」

**背景**：ARCHITECTURE.md 5.3 原文写的是「指针事件在 iframe 内捕获，经私有端口移动宿主。若跟手性不够，改为宿主侧不可见把手」。第一版实现按原文在小窗 iframe（`FloatApp.tsx`）内用 `setPointerCapture` 捕获拖动条/缩放角的指针事件，经私有端口（`FLOAT_PORT`）把位移/尺寸发给阅读器（`float-host.ts`）移动宿主 div。

**e2e 实测发现**：缩放用例稳定失败——`pointerdown` 能收到，但拖动方向一旦让指针越过 iframe 当前渲染的物理边界（缩放时「往外拖大」几乎立刻发生，因为缩放的方向就是让窗口变大，指针必然先走到当前尺寸之外），后续 `pointermove` 就不再送达 iframe 内的监听器。

**根因核实**（而不是猜测或绕过）：

- 搜索确认这是 pointer capture 跨 `iframe` 边界的已知限制，不是实现 bug：W3C pointerevents 仓库 issue #493「even with pointer capture on full width/height element in iframe, dragging stops working outside of iframe」；Chromium 对跨 frame 的 pointer capture 路由有专门的历史修复（issue 40615696「setPointerCapture doesn't work across iframes」），且那些修复针对的是同源/同进程场景，本项目的小窗是 `chrome-extension://` 源嵌入 `https://` 页面，跨源更严格。
- 用 CDP 直接构造并派发 `pointerdown`（设置 `isTrusted` 失败后改走真实 `page.mouse` 事件）复现：拖动条（顶部，区域内移动）用小位移能工作，但往外扩大窗口的缩放角用真实鼠标操作必然失败——与理论一致。

**采纳架构自带的退路**：5.3 原文已经预留「若跟手性不够，改为宿主侧不可见把手」，这正是该场景。调整为：

- `src/page/float-host.ts`：在宿主 div 的封闭 shadow root 里，iframe 之后追加两个不可见的叠加元素（`data-testid="float-drag-handle"` 顶部整行、`data-testid="float-resize-handle"` 右下角 16×16px），指针事件直接在宿主侧（页面脚本，`page/` 层，同一个文档）捕获，不再进 iframe，从根上避开跨 iframe 边界的限制。
- 手势结束（`pointerup`/`pointercancel`）后，通过 `FloatHostApi.onRectSettled` 回调把最终 rect 报给 `float-port.ts`，经私有端口（`ReaderToFloat` 的 `float/rect` 消息，新增 `settled: boolean` 字段）通知小窗；小窗收到 `settled: true` 才落盘 `settings.float.rect`——写入必须由小窗（扩展页面，可信上下文）做，阅读器所在的内容脚本在 `storage.local` 收紧为 `TRUSTED_CONTEXTS` 后读不到也写不了（5.11）。
- 连接时的一次性「恢复记忆位置/尺寸」（`settings.float.placement === 'remembered'` 或记了尺寸）仍然经私有端口的 `float/resize` / `float/reposition` 消息完成——这是一次性指令，不是连续拖动，不受上述限制影响，继续按原设计走私有端口。
- 移除了私有端口协议里的 `float/move`（见下方「契约改动」），因为连续拖动已经不再经过这个端口。

**代价**：把手完全不可见（无视觉提示，只有鼠标悬停时的 `cursor: move`/`cursor: nwse-resize`），这是用户体验上的一个需要过目的细节（见「需要用户确认」）。

## 发现：Chrome 原生不支持非可编辑文字的 Shift+方向键选区扩展

**背景**：最初按常见理解写了「鼠标点一下定位插入点 → Shift+方向键扩展选区」的用例，在真实 Chrome（含 Chrome for Testing 与 Edge）上稳定失败：选区长度在按键前后完全不变。

**核实**：搜索确认这是 Chrome 的既定行为，不是测试写法问题——Chromium 源码注释明确写着「for non-editable content, selection editor commands are disabled」，默认只有开启「光标浏览」（Caret Browsing，F7 或 `chrome://settings/accessibility` 里的「使用文本光标浏览网页」）后，Shift+方向键才能在普通页面文字上扩展选区；这是 Chrome 的无障碍设置，不受网页或扩展控制。`Selection.modify('extend', ...)` API 受同一限制，直接调用同样不生效。CDP 的 `Input.dispatchKeyEvent` 只影响渲染进程，不能触发浏览器 UI 级的 F7 加速键，所以也无法在自动化里打开光标浏览模式来复现「真实按键」路径。

**测试调整**：改为用 `Selection.setBaseAndExtent`（不受上述限制的底层 API）直接构造出「用户已经用键盘扩选到了某个范围」的最终选区状态（和用户真正打开光标浏览后按几次 Shift+方向键得到的 `Selection` 状态等价），再发一次真实的（`isTrusted`）按键事件触发哨兵的 `keyup` 监听，验证的是我们代码对「键盘来源的选区变化」的反应，而不是去验证 Chrome 自己的光标浏览功能（那不是我们能控制或需要测的东西）。哨兵的监听本身是来源无关的（`evaluateSelection` 只看 `window.getSelection()` 的内容，不关心是鼠标还是键盘改的），所以这个测试方式能如实验证我们的行为。

**产品影响**：如果用户没有打开 Chrome 的「光标浏览」，纯键盘用户确实无法用 Shift+方向键在页面上选中文字（这是浏览器限制，不是本扩展的缺陷，也不是本扩展能修复的）；打开光标浏览后，选区变化的监听机制已经验证可用。

## 需要用户在真机上确认的事项（尽量精简）

1. **拖动条 / 缩放把手做成完全不可见**（只有悬停时鼠标指针变成「移动」/「缩放」形状，没有任何可见的边框或背景色提示）——这是按「5.3 架构原文已预留的退路」和「尽量不喧宾夺主」定的，但用户可能更想要一点视觉提示（哪怕只是悬停时露出一条细线）。如果想要视觉提示，告诉我大概想要什么样子即可，改起来很小。
2. **代码块复制按钮固定悬浮在代码块右上角**，点击后文字变「已复制」/「复制失败」，1.2 秒后恢复——这是常见做法，但按钮的具体位置、文案可以按喜好调整。
3. **200% 缩放的最终确认**：自动化测试用「视口减半」模拟缩放对布局的影响（CSS 像素减半和浏览器缩放对布局是等价的，但毕竟不是真的按 Ctrl+ 缩放），建议在真机上用 Ctrl+ 放大到 200% 实际试一次划词→问→小窗这条路，确认看着也顺眼。
4. **宿主网页弹出原生 `<dialog>` 时小窗完全不可交互**——这是浏览器原生模态的 top-layer 机制决定的（5.3 已预告），目前没有退路能让小窗在原生模态开着的时候继续可用。如果这种场景在目标用户的实际使用中比较常见（比如某些网站的登录弹窗、Cookie 同意框用的是 `<dialog>`），可能需要在产品层面接受「这种情况下先关掉对话框再用小窗」，无需现在改代码。

## 是否需要修订架构 / 需求 / 最低版本

**需要**：建议下次修订 `ARCHITECTURE.md` 5.3 时，把「若跟手性不够，改为宿主侧不可见把手」的「若」去掉——V-12 实测证明这不是偶发的「跟手性不够」，而是稳定可复现的浏览器限制（pointer capture 不跨 iframe 边界），对拖动和缩放都成立，应该直接写成「拖动与缩放在宿主侧用不可见把手捕获指针，不在 iframe 内捕获」，并把现在 5.3 里「指针事件在 iframe 内捕获」那句改掉或标注为「已否决的设计，见 V-12」。不需要新增决策编号，只是把已经预留的退路从「备选」转正为「唯一实现」。

## 复测（2026-11-21，用户 Edge 试用后的修复）

| 问题 | 原因 | 修复 | 验证 |
| --- | --- | --- | --- |
| 一按住拖动条或缩放把手小窗就消失 | 「点网页别处收起」把小窗外壳也算成别处 | 外壳上的按下不收起 | e2e 断言拖动、缩放后小窗仍打开；用户 Edge 实测通过 |

| 拖过后收起再打开，位置回到选区旁边（大小记住了） | 每次打开都贴着选区重新摆放 | 同一页面里拖过就保持位置 | e2e「拖过之后收起再打开」，不带修复时失败 |
