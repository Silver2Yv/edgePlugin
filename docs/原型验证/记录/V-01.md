## 1. 方法：如何在没有调试器挂着的情况下测后台生命周期

`prototypes/net-probe/RESULT.md` 已经指出 Playwright 的 `launchPersistentContext` / `connectOverCDP` 常驻连接会让后台不被回收，导致长任务结论偏乐观。本次用了一个新方法验证并避开这一局限：

1. 用 `child_process.spawn(..., { detached: true, stdio: 'ignore' })` 起一个**分离的**浏览器子进程（`--remote-debugging-port=<固定端口>`），`child.unref()` 后 Node 脚本立刻退出。
2. 浏览器进程本身不受 Node 退出影响，独立运行；因为发起连接的 Node 进程已经整个退出，Chrome DevTools Protocol 的 WebSocket 连接自然断开，不存在"调试器常驻"的情况。
3. 等待若干秒（跨 30 秒/5 分钟阈值）。
4. 用**另一个全新的** Node 进程 `chromium.connectOverCDP` 重新接上同一个端口，读取结果。

脚本：`prototypes/v01-lifecycle/probe.mjs`（`control-launch`/`control-check` 做空闲回收的对照实验；`long-launch`/`long-launch-closed`/`long-check`/`long-check-closed` 做长任务实验；`cleanup` 收尾）。

### 1.1 对照实验：证明方法本身有效

先验证"等待期间真的没有调试器连着、后台确实被回收"这件事本身可信，而不是直接假设。

| 浏览器 | 做法 | 空闲等待 | workerEpoch 变化 |
| --- | --- | --- | --- |
| Chrome for Testing 159（headless=new） | 启动后立刻读一次 `workerEpoch`，脚本退出；等待后用新进程重连，先调一次扩展接口唤醒再读 | 75 秒 | `1b195459-…` → `26f35466-…`，**变了** |
| Microsoft Edge 157.0.4341.60（真实窗口，非 headless） | 同上 | 80 秒 | `a6408a89-…` → `e5bacd96-…`，**变了** |

两个浏览器都确认：没有调试器连着时，后台在远超 30 秒空闲阈值后被回收重启，`workerEpoch` 随之变化。这证明了后面长任务实验里"没有调试器常驻"的前提是真实成立的，不是自我声称。

## 2. 长任务（> 5 分钟）：检查点能否撑过去

架构 5.5 的检查点设计（每 1.5 秒写一次 `storage.session`，这是扩展接口调用，副作用是重置 30 秒空闲计时）是否真的能让一个纯网络流式任务在**无调试器、无 UI 订阅、源标签页已关闭**的情况下撑过 5 分钟，是本条最核心的待证命题。

模拟服务：`mock-relay` 的 `long` 模式，持续输出 330 秒（超过 5 分钟）。

| 浏览器 | 场景 | 已过时间 | 结果 |
| --- | --- | --- | --- |
| Chrome for Testing 159（headless） | 收到第一条正文增量后**关闭源标签页**（销毁小窗 iframe 和它的长连接端口），用分离进程方法等待，期间无任何调试器 | 480 秒 | 任务 `state: completed`，`workerEpoch` 与接单时一致（**没有被回收打断**） |
| Microsoft Edge 157（真实窗口） | 同上，关闭源标签页 | 370 秒 | 任务 `state: completed`，`workerEpoch` 未变 |
| Microsoft Edge 157（真实窗口） | 收到第一条正文增量后把源标签页 `location` 导航到 `about:blank`（销毁小窗 iframe、无 UI 订阅，但浏览器应用本身留一个空白窗口不整体退出） | 368 秒 | 任务 `state: completed`，`workerEpoch` 未变 |

**结论：检查点机制本身有效**——在无调试器、无界面订阅、源标签页已关闭/导航走的条件下，纯靠 `checkpointMs`（1.5 秒）的 `storage.session` 写入就能让后台撑过 5 分钟以上的流式任务，不需要额外的 20 秒保活调用兜底（5.5 里 keepaliveMs 的保活与 checkpoint 作用重叠，checkpoint 间隔更密，实际上是它在撑住空闲计时；详见第 5 节"对架构的回写建议"）。

### 实测中的工程坑（供复现参考，已在脚本里避开）

- Edge 真实窗口模式下，关闭最后一个标签页会让浏览器应用整体退出（不是后台被回收，是进程本身没了），那样测的就不是"后台在无 UI 时能否撑完"，而是污染了结论。脚本里关标签页前先留一个空白页，或改用导航到 `about:blank` 而不是真的 `close()`。
- `context.serviceWorkers()[0]` 在 Edge 上可能拿到不相关的内置 Service Worker，需要按 URL 过滤出扩展自己的那个。

## 3. 等响应头的连接超时（本次新补的行为）

**背景**：Chrome 官方文档（`extensions/develop/concepts/service-workers/lifecycle`）列出三条独立的回收条件：空闲 30 秒、单事件处理 5 分钟、**`fetch()` 响应头 30 秒未到达**。第三条和"空闲 30 秒"不是一回事——即使保活/检查点一直在重置空闲计时，`fetch()` 本身等响应头超过 30 秒浏览器仍可能把后台连同这次请求一起回收。架构原文承认"该后两者以检查点和 interrupted 为契约"，但没有给出一个主动的、用户能看懂的提示；原来的代码里发起请求后没有任何超时控制，只能等浏览器把后台整个回收掉、下次唤醒时才被动发现"interrupted"。

**本次实现**：在 `src/background/jobs.ts` 的 `run()` 里加了一个独立的连接计时器（`JOB_LIMITS.connectTimeoutMs`，默认 28 秒，见 `src/core/domain/job.ts`），从发起 `fetch` 到拿到响应头之间计时；拿到响应头立刻 `clearTimeout`。超时就主动 `abort()` 并把任务标成 `failed(timeout)`，界面文案「等待超时」。首条内容到达之后的沉默**不受此计时器约束**（只在等响应头阶段生效），避免违反架构"不能单凭沉默断言被拦"的要求。

| 用例 | 结果 |
| --- | --- |
| 单测：`hangForever` 模式模拟 fetch 永不 resolve，`askConnectTimeoutMs` 调小到 20ms | `failed`，`error.kind === 'timeout'`，请求 signal 已 `aborted` |
| 单测：响应头正常到达后，正文迟迟不来 | 60ms 后状态仍是 `streaming`，没有被连接超时误伤 |
| e2e（真实未缩放时间，`tests/e2e/lifecycle.spec.ts`）：head35 模式服务端故意 35 秒才给响应头，生产默认的 28 秒超时（未覆盖） | Chrome for Testing：29.3 秒内变成 `failed`，界面显示「等待超时」；Edge 157：29.6 秒内同样结果 |

**为什么选 28 秒而不是更保守的数字**：28 秒比浏览器的 30 秒回收阈值略短，目的是让用户先看到扩展自己给出的、脱敏的"等待超时"提示，而不是让浏览器先一步把整个后台回收掉、用户只能在下次唤醒时看到一句"上次请求的结果未知"。这个数值目前是经验值，不是从大量真实网络环境统计出来的，如果以后发现公司中转站在正常情况下首字节经常超过 25 秒，需要重新评估。

## 4. 其余模拟模式（head65/silent65/slowJson/heartbeat/crlf/split/streamError/disconnect/html200/401/403/404/405/param400）

这些模式在架构落地前就已经有覆盖：`tests/unit/core/chat-completions.test.ts`（流式解析在随机网络块切分下的稳定性、响应头分类）、`tests/unit/mock-relay.test.ts`（中转站本身行为）。本次没有改这部分解析逻辑，没有理由重跑，直接复用其结论：

- head65、slowJson 与 head35 走同一条连接超时逻辑（响应头延迟 > 28 秒即超时），不单独重测，结论类推成立。
- silent65（响应头立即到、正文沉默 65 秒）：单测已验证"响应头到达后连接超时解除、正文沉默不受此限制"，现网行为上这类任务会一直停留在 `streaming`，直到真的超过 5 分钟单事件上限或后台被回收，这正是架构希望的"列出可能性，不断言被拦"。
- heartbeat/crlf/split：SSE 解析对换行与网络块切分的容忍性，已有基于真实 mock-relay 响应、多随机种子切块的单测覆盖，结论稳定。
- streamError/disconnect：已有单测覆盖"流中错误保留已收到内容、中断给 streamBroken"；`disconnect` 模式衍生出新的 `failOnce` 模式用于验证 V-03 的重试闭环（见 V-03.md）。
- html200/401/403/404/405/param400：响应头分类表已有单测逐条覆盖，未改动。

## 5. 对架构的回写建议（不是本次已做的改动，供用户确认）

1. **5.5 的"保活"结论可以收紧**：原文说"每 20 秒调用一次扩展接口重置 30 秒空闲计时"。实测证明真正撑住空闲计时的是更密集的 `checkpointMs`（1.5 秒）写 `storage.session`，20 秒一次的 `keepaliveMs` 常量目前代码里没有被单独使用（历史遗留，见 `job.ts` 注释）。建议要么删掉未使用的 `keepaliveMs`，要么明确写清楚"检查点兼任保活，不需要额外的 20 秒心跳"。本次只加了注释说明，没有删常量（保持小改动）。
2. **新增的"连接超时"需要正式写进 5.5**：原文只提到"`fetch` 响应头超过 30 秒未到达"是回收条件之一，归在"以检查点和 interrupted 为契约"里，但没有描述一个主动超时。这次新补了一个独立于保活/检查点的 28 秒连接超时，建议把它写成 5.5 的正式契约，而不只是代码注释。
3. **28 秒是经验值**：需要用户确认是否要在真实公司网络（UniVPN/公司 WiFi）下采样首字节延迟分布后再校准这个数字；目前没有这类统计数据。
