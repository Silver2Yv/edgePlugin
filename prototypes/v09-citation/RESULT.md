## 第一部分：引用标记写法实测

### 方法

4 种候选写法 × 2 个模型（公司中转站 / deepseek-flash，DeepSeek 官方 / deepseek-v4-pro）× 2 种任务（总结打编号、问答逐字引用），每格 18 次总结 + 18 次问答 = 36 次响应，共 288 次生成调用，全部真实调用，0 次失败。随后对每条响应取第一个"可定位"的引用，送第三方裁判（DeepSeek 官方 + deepseek-flash，与两个被测对象都不完全相同）判断"引用位置是否支持结论"，共 273 次裁判调用，0 次失败。裁判结果按格抽样 20%（54 条）人工复核。

4 种写法：
- `bracket-id`：双方括号编号 `[[12]]`，逐字引用 `[[12]]原文[[/12]]`
- `fullwidth-bracket`：全角括号编号 `【12】`，逐字引用 `【12】原文【/12】`
- `cite-tag`：类 HTML 标签 `<cite b="12">内容</cite>`（总结场景整条要点包在标签内）
- `caret-id`：裸编号 `^12`，逐字引用 `「原文」^12`

|---|---|---|---|---|---|---|---|---|---|

8 格调用失败率均为 0。编造率（引用发送集合外编号）全部为 0——四种写法在本次样本规模下都没有观察到编造。

流式解析稳定性（results/streaming-stability.json，对真实响应文本做随机 chunk 边界重放，每写法 12 条响应 × 6 次重放 = 72 次试验）：4 种写法 `totalFlips` 均为 0，`allFinalMatchAlways` 均为 true。但本次样本块数都在个位数以内，caret-id 的裸编号写法在块数达到两位数（如 `^12` 在流中先被解析成 `^1` 再追加 `2`）时存在已知的"先出现再反转"风险，这次样本规模没有触发。

20% 人工复核（results/human-review-agreement.json，54 条抽样）：与裁判一致率 96.3%（52/54），两处分歧都是裁判偏严格（把足够支持的片段判成"不确定/不支持"），没有出现裁判偏宽松的情况。

### 推荐写法：全角括号编号 `【12】`

理由：
1. 与 Markdown 语法零冲突——不像双方括号 `[[ ]]` 容易被联想成 wiki 链接语法，也不像裸编号 `^12` 存在跟某些 Markdown 方言的上标语法 `^文字^` 撕裂的风险；
2. 有明确的起止分隔符（`【】`），流式解析天然安全，不存在裸编号那种"数字位数增长导致已输出结果反转"的结构性风险；
3 实测指标全面最好或接近最好：两个模型的总结/问答格式遵守率均为 1.0（仅官方问答 0.8889），编造率 0，逐字准确率 0.9375~1.0，可定位率 0.9894~1.0，裁判支持率 0.9722/1.0。

次选：`bracket-id`（双方括号），指标同样优秀，仅在视觉上与 wiki 链接语法更接近，若产品侧已有双方括号的其他用途需避让。

不推荐用于正式方案：
- `cite-tag`：总结场景要求模型把整条要点包进标签，公司中转站模型的总结格式遵守率只有 0.6667，明显落后于其他三种写法；
- `caret-id`：虽然本次实测指标满分，但裸编号在块数达到两位数后有流式解析反转的结构性风险，不适合文档较长、块数较多的真实场景。

### 推荐 Prompt 片段

```
引用标记写法：全角方括号编号。
- 总结要点：每条要点末尾追加形如 【12】的标记，12 替换为该要点依据的资料块编号；
  多个块写成 【12,5】。
- 逐字引用：把逐字摘录的原文片段用同一编号前后包住，写成
  【12】被逐字摘录的原文片段【/12】，中间内容必须是资料原文的连续子串，不能改写。
- 编号必须是本次提供的资料块编号之一，禁止编造资料里不存在的编号。
```

### 推荐解析正则

```javascript
// 逐字引用（标记内为原文片段）
const fullwidthQuoteRe = /【([0-9]+)】([\s\S]*?)【\/\1】/g;
// 要点末尾编号（含多编号 【12,5】）
const fullwidthNumberRe = /【([0-9]+(?:\s*[,，、]\s*[0-9]+)*)】/g;
// 解析顺序：先扫描 quoteRe 并记录命中区间，再扫描 numberRe，跳过与 quoteRe 命中区间重叠的匹配，
// 避免逐字引用内部出现的块编号被二次误判为"要点编号"标记。
```

## 第二部分：锚点匹配与降级算法

### 方法

纯 TypeScript 原型，位于 `prototypes/v09-citation/anchor/`。锚点结构包含：精确文本（exactText）、前后约 32 字上下文、块摘要（blockDigest）、标题链、滚动比例（scrollRatio）、块内偏移（blockOffset）。三级降级：
1. 精确匹配：全块范围找 exactText 精确子串，重复命中用前后文做消歧（编辑距离差 ≤1 判歧义）；
2. 候选块内近似匹配：用 `approx-string-match`（npm，版本 2.0.1，MIT 许可，单维护者）做近似匹配，编辑距离阈值取 exactText 长度的 20%（下限 1，上限 20），候选最少错误数与次少错误数之差 ≤1 判歧义，不强行选一个；
3. 都失败按 scrollRatio 兜底，仅给粗略位置、弱提示；
4. 彻底无候选（如锚点所属 frame 不存在）→ unresolved，调用方视为不可点击。

版本绑定前置校验（blockId 是否在发送集合内、contentVersion 是否仍是当前版本）在 `validate.ts`，不通过直接短路，不进入三级匹配流程。

### 测试结果

`npm run anchor:test`（`vitest run --config anchor/vitest.config.ts`）：3 个测试文件，16/16 全部通过，耗时 653ms。
- `frame.test.ts`（2 项）：多框架场景
- `validate.test.ts`（5 项）：无效 blockId、过期 contentVersion、编号仅在发送块集合内有效等版本绑定校验
- `match.test.ts`（9 项）：插入/删除段落、重复句子、精确匹配、近似匹配命中、近似匹配失败兜底滚动比例等场景

### 性能实测

`npm run anchor:bench`（`tsx anchor/src/bench.ts`），合成文档 42017 字，切成 77 块（每块 550 字，落在架构 300~800 字区间内），每场景跑 20 次：

| 场景 | 平均耗时 | p95 | 最快 | 最慢 |
|---|---|---|---|---|
| 精确匹配命中 | 0.997ms | 4.041ms | 0.730ms | 4.041ms |

1~5 万字文档规模下，三种场景均在毫秒级（p95 均 <5ms），满足交互场景的延迟预期。

## 风险与说明

1. **裁判方法学限制**：裁判固定用 DeepSeek 官方 + deepseek-flash，与两个被测对象存在"同模型不同网络"（对公司中转站/deepseek-flash）或完全独立模型（对 deepseek-v4-pro）的不对称重叠，单裁判模型本身也有主观性。已用 20% 人工抽样复核缓解，一致率 96.3%，且仅发现裁判偏严格、未发现偏宽松，可支撑"该方法基本可用，但正式阶段仍建议保留人工抽样复核"的结论。
2. **cite-tag 总结场景遵守率偏低**：该写法要求模型把整条要点包进标签，公司中转站模型（deepseek-flash）执行时遵守率仅 0.6667，明显弱于其他三种写法，已据此不推荐作为主写法。
3. **caret-id 裸编号的流式反转风险**：本次真实样本块数均为个位数，72 次流式重放试验显示 0 次反转，但裸编号写法在数字位数增长时（如 10 以上编号）存在"先解析出单数字再被追加数字反转"的结构性风险，仅因本次样本规模未触发，不代表该写法在块数更多的真实文档上同样安全，已据此不推荐。
4. **approx-string-match 维护状态**：当前版本 2.0.1，MIT 许可，单维护者，长期维护性需要关注，但该库逻辑简单（近似字符串匹配），即便停止维护也可在需要时自行内置替代实现，风险可控。
5. **anchor 算法的已知盲点（继承自原实现设计记录，本次复核确认存在，未改动）**：块摘要（blockDigest）对块内局部文字漂移不敏感（整块摘要只能检测块级变化，无法精确定位块内小范围改动）；近似匹配阶段优先扫描锚点记录的 blockId 对应块，找不到才退而扫描全部块，存在"候选块本身被错误标注"时的查找顺序假设依赖。
6. **过往测量问题已发现并修正**（供复核留痕）：原判断逐字准确率的代码未区分"问答逐字引用"与"总结场景改写转述"，裁判阶段曾因字段名误用（`r.taskType` 应为 `r.task.taskType`）导致全部总结任务被错误送入问答裁判模板、以及 cite-tag 写法因整条要点包标记导致"行减标记"算法回收不到有效结论文本，均已定位并修正，修正后数据已体现在上表中。
